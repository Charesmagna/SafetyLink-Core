# SafetyLink-Core Repository Audit — 2026-11-04

**Repository:** `Charesmagna/SafetyLink-Core`  
**Audited baseline:** `beta` at `5b2de65bc3c6544e77ee61e627c9c40aad0ab882`  
**Audit branch:** `audit/2026-11-04-repository-audit`  
**Audit type:** Static source/configuration review  
**Production changes:** None  
**Runtime tests / live provider tests:** Not run

## Executive assessment

**Release readiness: BLOCKED for real emergency operations until the critical security and dispatch findings below are remediated and verified.**

The repository contains substantial product implementation: React/Vite, Capacitor, native Android services, a Cloudflare Hono Worker, an Express server, multiple communications providers, offline queues, and PWA/marketing pages. The issue is not absence of features. The issue is that several independent implementations overlap, and important paths report success without proving the operation succeeded.

The most urgent risks are:

1. Firestore security rules currently permit unauthenticated read and write access to every document.
2. A release signing keystore is committed in the repository and the signing passwords are hardcoded in source/workflow configuration.
3. The Cloudflare Worker uses unsigned Base64 JSON tokens and weak password hashing.
4. Multiple emergency and data-management endpoints lack authentication and tenant-level authorisation.
5. The dispatch pipeline, offline queue and native SMS implementation contain false-positive success states.
6. The Rain/Please Call Me path has a schema defect and does not yet prove that outbound SMS uses the user's Rain SIM plan.

This audit does not establish that the live production Worker or current provider accounts are exploitable or failing at this exact moment. It establishes that the checked-in source contains the conditions described below. Live configuration and runtime behaviour still need controlled verification.

## 1. Critical findings

### C-01 — Firestore database is configured for public read/write

**Evidence:** `firestore.rules`

The catch-all rule grants read and write access to every document without checking authentication, user identity, organisation membership or role.

**Impact:** If the deployed Firebase project uses these rules, any party able to reach the Firestore database can read, modify or delete application data. This can include user profiles, organisation data, location information and incident records.

**Required action:**
- Immediately replace the catch-all rule with deny-by-default rules.
- Require authenticated users and validate ownership/organisation membership for every collection.
- Restrict administrative writes to trusted server-side code.
- Add Firebase Emulator rule tests for cross-user and cross-tenant access.
- Verify deployed rules in Firebase Console; repository rules alone do not prove what is currently deployed.

### C-02 — Android release signing material is stored in Git

**Evidence:**
- `.github/secrets/release-keystore.b64` exists in the repository.
- `android/app/build.gradle` contains hardcoded release store/key passwords.
- `.github/workflows/build-apk.yml` decodes the committed keystore and writes signing properties containing fixed passwords.
- Root `.gitignore` does not exclude `.github/secrets/`.

**Impact:** Repository access exposes the signing material and password. A compromised signing key can undermine APK authenticity and update trust.

**Required action:**
- Treat the signing material as compromised.
- Establish whether Google Play App Signing is enabled and whether this is the app-signing key or an upload key before rotating anything. Do not blindly replace the key: sideloaded installations may reject updates signed with a different key.
- Move signing material to protected GitHub Actions secrets or a dedicated signing service.
- Remove the keystore and passwords from current source and clean the Git history.
- Verify the new signing process against an existing installed APK before publishing.

### C-03 — Cloudflare Worker authentication tokens are forgeable

**Evidence:** `worker/src/index.ts`, token helpers near the top of the file.

The Worker creates tokens by Base64-encoding JSON claims and verifies them by decoding JSON and checking an expiry value. There is no cryptographic signature verification. The password hash helper uses SHA-256 with a shared server secret as salt rather than a password-hashing function designed to resist offline guessing.

**Impact:** A caller can construct token payloads with chosen user, organisation or role claims. Because some privileged routes rely on token claims, this undermines the authorisation boundary. The password storage method is also unsuitable for production credentials.

**Required action:**
- Replace with a signed, expiring JWT using a maintained library and strong key management, or opaque server-side sessions.
- Use Argon2id or an appropriately configured bcrypt/scrypt password hash.
- Validate token issuer, audience, expiry, subject, role and organisation on every request.
- Rotate the signing secret after deployment and invalidate old tokens.
- Do not trust organisation or role fields supplied by the client.

### C-04 — Worker routes expose emergency and user-data operations without authentication

**Evidence:** `worker/src/index.ts`

The following routes are defined without `authMiddleware` or an equivalent verified user/session check:

- `POST /api/panic`
- `POST /api/incidents`
- `POST /api/user/heartbeat`
- `POST /api/sync/offline`
- `POST /api/profile/sync` (uses a profile token, but the initial phone claim is not independently verified)
- `POST /api/pcm/locate`
- `GET /api/init-db`

The heartbeat route accepts a user ID and location from the request and updates that user record. The panic route accepts caller identity and emergency-contact numbers from the request. The offline sync route trusts the supplied organisation ID.

**Impact:** Unauthenticated callers can attempt to create incidents, trigger provider traffic, alter another user's location/status, claim profile phone numbers, submit records under arbitrary organisations or repeatedly invoke database initialisation.

**Required action:**
- Require a verified user/device identity for app-originated panic, heartbeat, incident and sync endpoints.
- Use a separate signed webhook credential for Rain/SMS Gateway callbacks.
- Require phone ownership verification before issuing the first profile token.
- Protect database migrations/initialisation with deployment-only credentials; remove public GET initialisation.
- Apply rate limits and idempotency after identity verification, not solely to caller-supplied phone numbers.

### C-05 — Organisation routes do not consistently enforce tenant ownership

**Evidence:** `worker/src/index.ts`, routes for `/api/org/:orgId/members`, `/api/org/:orgId/incidents` and incident resolution.

These routes check that a token is present and decodable, but do not consistently compare the authenticated organisation claim with the organisation ID in the URL. Incident resolution updates by incident ID without an organisation condition. The unsigned token issue further undermines the super-admin check.

**Impact:** Cross-tenant data access or modification is possible at the application logic layer.

**Required action:**
- Derive organisation scope from the verified session, not the URL.
- Enforce `session.orgId === requestedOrgId` for organisation-scoped operations.
- Include organisation scope in every SQL update/delete predicate.
- Define explicit role permissions for user, dispatcher, guard/patroller, organisation admin and super-admin.
- Add automated cross-tenant denial tests.

## 2. High-priority emergency dispatch findings

### H-01 — Dispatch pipeline marks incidents processed without inspecting provider results

**Evidence:** `src/services/panic-alert.ts`

The service runs VAPI, Bland, Twilio and Infobip calls using `Promise.allSettled()`, but does not inspect each fulfilled/rejected result before updating the incident to `PROCESSED`. Telegram is fire-and-forget.

**Impact:** An incident can be recorded as processed even when every provider call failed. The current status does not mean responders were notified.

**Required action:**
- Persist one canonical incident ID and one result row per target/provider/channel.
- Inspect every provider result.
- Use truthful states such as `QUEUED`, `SUBMITTED`, `FAILED`, `PARTIAL`, `DELIVERED` and `ACKNOWLEDGED`.
- Distinguish provider API acceptance from carrier delivery, call answer and human acknowledgement.
- Never report `PROCESSED` merely because a request was attempted.

### H-02 — Offline incident queue reports a dispatched state before dispatch

**Evidence:** `android/app/src/main/java/com/aistudio/safetylink/vqnztp/data/OfflineSyncWorker.java`

The local queue payload is written with `status = DISPATCHED` before the backend sync occurs. The Worker endpoint `POST /api/incidents` catches database errors and still returns `ok: true` / `RECORDED`. The offline sync endpoint also returns the submitted payload length as `synced` while swallowing insert failures.

**Impact:** An offline incident can be represented as dispatched or synced when it is only stored locally or when backend persistence failed.

**Required action:**
- Queue as `QUEUED_OFFLINE`, not `DISPATCHED`.
- Require a persisted server acknowledgement with the canonical incident ID before removing a local item.
- Return per-item success/failure and retain failed items.
- Add idempotency keys and exponential backoff.
- Do not swallow database errors and then return success.

### H-03 — Native Android SMS reports SENT immediately after modem submission call

**Evidence:** `android/app/src/main/java/com/aistudio/safetylink/vqnztp/EmergencyService.java`

The method creates sent PendingIntents and calls `SmsManager.sendMultipartTextMessage()`, then immediately returns `SENT`. No matching `SMS_SENT` BroadcastReceiver or result handler is present in the checked native source/manifest.

**Impact:** The application does not reliably record the Android SMS send result. Even a successful `SmsManager` submission is not proof of carrier delivery or recipient receipt.

**Required action:**
- Register a receiver for every multipart message part and aggregate all part results.
- Add a bounded timeout and persist the result.
- Keep `SUBMITTED`, `SENT_TO_NETWORK` and `DELIVERED` distinct.
- Add delivery receipts only where the carrier/provider supports them.

### H-04 — Multiple dispatch implementations compete

**Evidence:**
- `src/services/panic-alert.ts`
- `src/utils/store.ts`
- `src/services/NativeDispatchService.ts`
- `android/.../EmergencyService.java`
- `android/.../EmergencyDispatchPlugin.java`
- `server.ts`
- `worker/src/index.ts`

There are multiple independent dispatch entry points and backend/provider implementations. The React store has a telemetry stub that returns `true` without performing telemetry. The Express server and Cloudflare Worker both expose emergency-related APIs.

**Impact:** Different trigger paths can create different incident IDs, send duplicate alerts, disagree about success and bypass shared policy.

**Required action:**
- Define one documented incident contract and one canonical server-side orchestration path.
- Keep native Android responsible for local trigger, local persistence and direct GSM fallback.
- Route network dispatch through a single authenticated API.
- Treat Rain PCM as a separate authenticated inbound trigger adapter that enters the same incident coordinator.
- Remove no-op success stubs from production code.

### H-05 — Browser call path can report success when only the dialler was opened

**Evidence:** `src/services/NativeDispatchService.ts`

The non-native `placeCall()` path opens a `tel:` link and returns `success: true`, `simulated: false`, `INITIATED`. Opening a dialler does not prove a call was placed or connected. The WhatsApp path similarly treats opening an intent as a sent message even though the plugin interface exposes `requiresManualSend`.

**Required action:**
- Report `DIALER_OPENED` and `WHATSAPP_OPENED` with `requiresUserAction: true`.
- Never represent those states as a completed call or sent message.
- Propagate `requiresManualSend` from the native plugin.

## 3. Rain SIM / Please Call Me gateway

### H-06 — Zero-airtime contact schema does not match its insert statement

**Evidence:** `worker/src/zero-airtime.ts`

The `sl_contacts` table is created without a `name` column, but `syncProfile()` inserts into `name`. Contact synchronisation can fail with a missing-column error.

**Required action:** Add a versioned D1 migration for the missing column, validate it against an existing database, and make profile sync transactional or safely retryable.

### H-07 — Rain outbound SMS route is not proven to be the user's Rain SIM route

**Evidence:** `worker/src/zero-airtime.ts` and `worker/src/index.ts`

The outbound SMS code calls the SMS-Gate REST API, then Africa's Talking and Twilio fallbacks. The source comment describes an SMS-Gate monthly allowance. This does not prove that the request is routed through the Rain SIM with the unlimited SMS plan described by the product owner.

The inbound PCM webhook and outbound SMS sender are separate flows and must be verified separately.

**Required action:**
- Confirm the exact Rain SIM / SMS Gateway configuration and the outbound device/provider endpoint.
- Implement a dedicated Rain/SMS-Gate adapter with provider-specific credentials and truthful responses.
- Keep Twilio optional; do not require a paid Twilio upgrade for the core fallback.
- Test using an explicitly approved test destination only after the user authorises a real SMS test.

### H-08 — PCM webhook lacks replay protection and can return a false dispatch status

**Evidence:** `worker/src/index.ts`, `handlePcmWebhookInner()` and `worker/src/zero-airtime.ts`.

The webhook accepts a token or HMAC signature, but the signed request has no timestamp/nonce replay window. A valid signed request can be replayed. The wrapper catches internal errors and returns HTTP 200. The inbound handler returns `DISPATCHED` without requiring at least one successful notification result.

**Required action:**
- Sign timestamp + body, reject stale requests and store a replay nonce/event ID.
- Return non-2xx on processing failure so the gateway can retry.
- Make PCM event creation idempotent.
- Return `ACCEPTED` or `PARTIAL` based on actual provider submissions, never unconditional `DISPATCHED`.
- Record each contact's notification result.

### H-09 — Gateway number configuration is not included in the Worker deployment secret loop

**Evidence:** `.github/workflows/deploy-worker.yml` and `worker/wrangler.toml`

The Worker reads `RAIN_GATEWAY_MSISDN`, but the checked deployment workflow's secret list/environment mapping does not provision it. The checked Wrangler config does not define it as a variable.

**Required action:** Verify the live Worker variable/secret. Add it to the controlled deployment configuration if it is absent. The gateway endpoint should fail clearly when the number is not configured.

## 4. Android and Bluetooth reliability

### H-10 — BLE GATT ownership is still attached to the Capacitor plugin

**Evidence:** `ITagPlugin.java`, `SafelinkForegroundService.java` and `BootReceiver.java`

GATT connections and callbacks are held in `ITagPlugin` instance maps. The foreground service calls the static `ITagPlugin.reconnectBondedDevices()`, but that method only reconnects when the plugin's static `instance` is non-null. The foreground service itself does not own the GATT client lifecycle.

**Impact:** The native service is not an independent BLE owner. Its recovery path depends on a Capacitor plugin instance being alive. This is a structural risk when the WebView/activity is destroyed or not initialised after boot.

**Required action:**
- Move scanning, GATT connection, notification subscription, reconnect and trigger handling into a service-owned native BLE manager.
- Let the Capacitor plugin communicate with that manager; do not let the manager depend on a WebView plugin singleton.
- Persist paired device identifiers and reconnect state.
- Add device-side tests for screen lock, app swipe-away, WebView recreation, Bluetooth toggle, process kill and reboot.

### H-11 — Foreground service type needs Android-version/policy review

**Evidence:** `AndroidManifest.xml`

The BLE sentinel and emergency services are declared as `specialUse`, not `connectedDevice`. The manifest includes special-use declarations but not the connected-device foreground service permission/type for the BLE monitoring service.

**Required action:** Review the exact Android target SDK and current Play policy. Use the correct foreground-service type and permissions for BLE-connected-device work where applicable, and document the permitted special-use case for any service that genuinely requires it. Do not assume that declaring `specialUse` makes persistent BLE monitoring acceptable.

### H-12 — Native countdown and button patterns do not match the agreed product behaviour

**Evidence:**
- `PanicService.java` starts at 10 seconds.
- `store.ts` defaults the app countdown to 5 seconds.
- `ButtonPatternDetector.java` defaults one press to panic, two presses to Find Phone, and three presses to Safety Timeout.

**Impact:** UI and native service behaviour can disagree. The configured defaults do not match the proposed one/two/three-press trigger scheme.

**Required action:** Define one canonical trigger state machine and timing contract, then make UI, iTAG detector, PanicService and notification actions use it. Preserve the currently working trigger behaviour until device tests confirm the replacement.

### H-13 — Hardcoded native emergency defaults

**Evidence:** `PanicService.java` contains default responder phone and organisation values. `EmergencyService.java` contains a fallback recipient and hardcoded caller identity values in its backend payload.

**Impact:** If an Intent omits a field, a live emergency may be routed to a stale/test destination or attributed to the wrong identity.

**Required action:** Require verified user profile, organisation, responder and contact data. If a required field is missing, preserve the local incident and report the missing configuration; never silently substitute a production recipient.

## 5. Backend, database and integration architecture

### H-14 — Express production database points to an ephemeral path

**Evidence:** `src/db/index.ts`

Production selects `file:/tmp/safetylink.db`. The `/tmp` directory is not durable storage in common container/serverless environments.

**Impact:** Data may disappear on instance replacement or restart. This is not suitable as the system of record for emergency incidents.

**Required action:** Select one durable production database and make it authoritative. Add migrations, backups, restore drills and persistence tests. Keep local SQLite only for development/test.

### H-15 — Multiple backends and persistence systems have overlapping responsibilities

**Evidence:** Root `server.ts`, `worker/src/index.ts`, `src/db/index.ts`, Firebase/Firestore initialisation, Supabase client initialisation, Cloudflare D1 and Redis/BullMQ code.

The codebase contains an Express backend and a Cloudflare Worker backend, alongside D1, libSQL/SQLite, Firestore, Supabase and Redis queue integrations.

**Impact:** It is unclear which service owns authentication, incidents, contact records, dispatch state and organisation membership. This creates drift and partial writes.

**Required action:** Define an explicit system-of-record matrix and migrate callers incrementally. Do not delete an existing backend until all clients have moved and parity tests pass.

### H-16 — Client-side integration secrets are stored in localStorage

**Evidence:** `src/utils/store.ts`

Integration configurations, including API keys/secrets, ConnectyCube auth secrets, Tuya secrets and ThingsBoard tokens, are persisted through localStorage-backed state. Integration secrets are also assembled into client-side dispatch payloads.

**Impact:** Any successful XSS or compromised browser context can read these values. Client-supplied provider credentials can also bypass server-side tenant/provider policy.

**Required action:** Keep provider secrets server-side. Store only non-secret provider configuration and opaque references in the client. Encrypt any unavoidable device-local credential using Android Keystore-backed storage and do not expose it to the PWA.

### H-17 — Provider health endpoint reports configuration, not operational health

**Evidence:** `worker/src/index.ts`, `GET /api/health/providers`

The Worker reports whether environment variables exist. This is not a provider connectivity, account status, number capability, SMS submission or call initiation test.

**Required action:** Label these values `configured`, not `operational`. Add safe, read-only diagnostics with clear last-checked timestamps and no secret leakage. Keep actual test messages/calls behind an explicit test action and approved destination.

## 6. Build, release and CI/CD

### H-18 — Production release workflow can publish from a manually selected non-production branch

**Evidence:** `.github/workflows/build-apk.yml`

The workflow triggers on pushes to `main`/`master` and also supports manual dispatch. It creates a GitHub Release and uploads APKs to the production R2 bucket. A manual run on a branch other than `main` publishes the v2 R2 object.

**Required action:**
- Do not manually run this workflow from `beta` or an audit/agent branch.
- Split debug/QA builds from signed production releases.
- Give beta a separate R2 bucket/prefix and separate Cloudflare staging Worker/D1 database.
- Require explicit release approval for signing and publishing.

### H-19 — Build and quality gates do not verify the complete repository

**Evidence:**
- Root `package.json` has no test script.
- `worker/package.json` has only dev/deploy scripts.
- Root `tsconfig.json` includes `src` and excludes several route/provider files; it does not type-check `server.ts` or `worker/src`.
- `.github/workflows/quality-gate.yml` runs `npm run lint` with `continue-on-error: true`.
- `.github/workflows/build.yml` invokes `npm run tauri:build`, but the root package scripts do not define `tauri:build`.

**Impact:** A passing web build does not prove the Express backend, Cloudflare Worker, Android Java/Kotlin or Tauri packaging is valid. The quality gate can pass even when TypeScript lint fails.

**Required action:**
- Add separate strict type-checks for web, Express and Worker.
- Add unit/integration tests for auth, tenant scope, incident idempotency, provider result aggregation, PCM replay handling and offline queue acknowledgement.
- Make required checks blocking on pull requests.
- Repair or remove the invalid Tauri build step.
- Use lockfile-based deterministic installs and pin action versions.

### H-20 — Existing audit documents are stale and contradict current source

**Evidence:** `AUDIT_REPORT.md` and `SAFETYLINK_AUDIT.md`

The existing documents describe the system as secured/ready for commercial deployment, but the current checked source still contains the open Firestore rules, signing-key exposure, unsigned Worker tokens, unprotected endpoints and false-positive dispatch states.

**Required action:** Treat earlier reports as historical notes, not release approval. Update them only after remediation and repeatable verification.

## 7. Product, PWA and marketing integrity

### M-01 — Synthetic telemetry is presented with operational language

The public homepage contains generated event rows and a ticker that labels multiple channels as `LIVE`, including channels whose real configuration/health is not established by the displayed component. It also displays precise latency and compliance/security claims.

**Required action:**
- Label demonstration telemetry explicitly as `DEMO` or `SIMULATED`.
- Only show real provider/device states when backed by recent server/device telemetry.
- Substantiate latency, encryption, device-rating and compliance claims before publishing them as facts.
- Preserve existing media and page content while improving its order and hierarchy.

## 9. Prioritised remediation sequence

### Phase 0 — Containment
1. Rotate exposed API credentials and secrets; remove credential material from `AGENTS.md` and Git history.
2. Assess release keystore exposure and plan safe signing-key replacement.
3. Lock down Firestore rules immediately after verifying the deployed project and preparing authenticated access rules.
4. Disable or protect unauthenticated administrative/mutation routes before any real customer deployment.

### Phase 1 — Identity and tenant security
1. Implement signed sessions/JWT and strong password hashing.
2. Enforce user/organisation/role scope at every API route and database query.
3. Add phone ownership verification for PCM profile enrolment.
4. Remove client-side secrets and demo/super-admin bypass paths from production.

### Phase 2 — Canonical incident and dispatch model
1. Establish one incident ID and one state machine.
2. Make provider results explicit and durable.
3. Fix native SMS send-result handling.
4. Fix offline queue state and acknowledgement.
5. Make duplicate suppression idempotent and ensure failed first attempts do not cause later alerts to be suppressed as if responders were notified.

### Phase 3 — Rain SIM and zero-airtime
1. Fix D1 contact schema with a migration.
2. Verify Rain inbound webhook payload and sender-number extraction against actual SMS Gate samples.
3. Confirm outbound Rain SIM routing and credentials.
4. Add replay protection, event idempotency and per-contact results.
5. Perform real SMS tests only to an explicitly approved destination.

### Phase 4 — Android and iTAG
1. Move GATT ownership into a native service-owned manager.
2. Align countdown and multi-press semantics.
3. Remove hardcoded recipient/organisation defaults.
4. Verify foreground-service types and permissions.
5. Test lock screen, process death, reboot, Bluetooth disable/enable and device reconnect on the target Android devices.

### Phase 5 — Release engineering and product
1. Add a separate beta Worker/D1/R2 deployment.
2. Add blocking quality gates and backend/native test suites.
3. Rework command centre and PWA using the existing design/content inventory.
4. Complete the public-site refresh after operational claims are accurate.

## 10. Verification boundary

This audit was performed against repository source/configuration using GitHub file and directory reads. It did **not**:

- run `npm install`, `npm run lint`, `npm run build` or Gradle;
- run Firebase rules tests or D1 migrations;
- query production Cloudflare secrets or database contents;
- send real SMS, place calls or trigger emergency alerts;
- test iTAG hardware or Android lock-screen behaviour;
- deploy a Worker, Pages site or APK;
- merge or modify `beta`, `main` or `master`.

The next engineering step is a controlled remediation branch for the critical security findings, followed by a staging environment and a repeatable test matrix. The current audit branch contains this report only; application source has not been changed by the audit.
